## Цель работы

Освоить работу с HTML-формами в PHP: отправку данных на сервер, их обработку и валидацию, сохранение в файл и вывод в таблице. Выполнены оба дополнительных задания (интерфейс валидаторов и ООП-реализация).

## Модель данных

| Поле | Тип | Описание | Ограничения |
|---|---|---|---|
| `title` | string | Заголовок записи | 3–80 символов, обязательное |
| `author` | string | Автор | 2–50 символов, обязательное |
| `entry_date` | date | Дата, к которой относится запись | формат `Y-m-d`, не в будущем |
| `mood` | enum (select) | Настроение | `great`, `ok`, `bad` |
| `tags` | enum (checkbox) | Теги, множественный выбор | `work`, `study`, `family`, `health` |
| `note` | text | Развёрнутая заметка | 10–1000 символов, обязательное |
| `created_at` | datetime | Время создания | ставится сервером |

Требования выполнены: 7 полей; есть string, date, enum (checkbox) и text.

## HTML-форма и клиентская валидация

Форма отправляется методом **POST** на ту же страницу (`action=""`). Атрибуты клиентской проверки:

- `required` — обязательные поля;
- `minlength` / `maxlength` — ограничения длины;
- `type="date"` и `max` — выбор даты не позже сегодняшней;
- `select` и `checkbox` — ограниченные наборы значений.

Клиентская проверка нужна только для удобства: её можно обойти, поэтому все правила повторяются на сервере.

## Обработка данных на сервере

1. Данные берутся из `$_POST`.
2. `FormHandler` нормализует значения (`trim` для строк, фильтрация массива `tags`).
3. Каждое поле проходит через цепочку валидаторов; на первой ошибке проверка поля прекращается.
4. При ошибках форма показывается снова: введённые данные сохраняются, рядом с полями выводятся сообщения.
5. При успехе добавляется `created_at`, запись сохраняется в `data.json`, затем выполняется редирект `?saved=1` (паттерн **Post/Redirect/Get**, чтобы обновление страницы не отправляло форму повторно).

## Архитектура (ООП + интерфейс валидаторов)

| Класс / интерфейс | Назначение |
|---|---|
| `App\Validator\ValidatorInterface` | Контракт: `validate(mixed $value): ?string` — возвращает текст ошибки или `null` |
| `RequiredValidator` | Поле не пусто |
| `LengthValidator` | Длина строки (`mb_strlen`, учитывает UTF-8) |
| `DateValidator` | Формат `Y-m-d`, реальная дата, не в будущем |
| `EnumValidator` | Значение (или все значения массива) входит в белый список |
| `FormHandler` | Нормализует данные и применяет правила `поле => [валидаторы]` |
| `JsonStorage` | Чтение и запись в JSON с блокировкой файла |

Благодаря интерфейсу новые правила добавляются отдельным классом без изменения `FormHandler`: достаточно реализовать `ValidatorInterface` и добавить объект в массив правил.

## Хранение данных

Формат — JSON (`JSON_PRETTY_PRINT | JSON_UNESCAPED_UNICODE`), читаемый человеком. Запись выполняется под `flock(LOCK_EX)`, чтобы одновременные запросы не повредили файл.

Пример:

```json
[
    {
        "title": "Хороший день",
        "author": "Ywxig",
        "entry_date": "2026-11-09",
        "mood": "great",
        "tags": ["study", "family"],
        "note": "Сдал лабораторную и погулял вечером.",
        "created_at": "2026-11-09 18:30:00"
    }
]
```

## Вывод и сортировка

Записи читаются из файла и выводятся в HTML-таблице со стилями CSS. Заголовок каждого столбца — ссылка `?sort=<поле>&dir=asc|desc`; повторный клик меняет направление, текущая сортировка отмечена стрелкой ▲/▼. Имя поля сортировки проверяется по **белому списку** колонок, произвольное значение игнорируется.

## Безопасность

- **XSS:** весь вывод проходит через `htmlspecialchars` (функция `e()`), включая значения, возвращаемые в форму.
- **Белые списки:** значения `mood`, `tags` и параметр `sort` принимаются только из заранее заданных наборов.
- **Валидация на сервере** независимо от клиентской.
- **Строгая типизация:** `declare(strict_types=1)`.
- **PRG:** защита от повторной отправки формы.

## Примеры работы

1. Пустая форма → браузер блокирует отправку (`required`).
2. Запрос в обход браузера (например, `curl` с датой `2099-01-01`) → сервер вернёт ошибку «Дата не может быть в будущем».
3. Корректные данные → сообщение «Запись успешно сохранена», запись появляется в таблице.
4. Клик по заголовку «Дата» → сортировка по возрастанию, повторный клик → по убыванию.

## Ответы на контрольные вопросы

### 1. Какие существуют методы отправки данных из формы на сервер? Какие методы поддерживает HTML-форма?

HTML-форма (атрибут `method`) поддерживает два метода: **GET** и **POST** (а также `dialog` для элемента `<dialog>`, который данные на сервер не отправляет). Другие методы HTTP (`PUT`, `DELETE`, `PATCH`) отправляются через JavaScript (`fetch`/AJAX) или эмулируются скрытым полем `_method` в фреймворках.

| | GET | POST |
|---|---|---|
| Где передаются данные | В URL (query string) | В теле запроса |
| Видимость | Видны в адресной строке, истории и логах | Не видны в URL |
| Объём | Ограничен длиной URL | Практически не ограничен |
| Кеширование и закладки | Возможны | Нет |
| Назначение | Получение данных, поиск, фильтры, сортировка | Создание и изменение данных, пароли, загрузка файлов |
| Идемпотентность | Да | Нет |

В этой работе форма добавления записи использует POST, а сортировка таблицы — GET, потому что она ничего не меняет и её удобно сохранять в закладках.

### 2. Какие глобальные переменные используются для доступа к данным формы в PHP?

- `$_POST` — данные, отправленные методом POST;
- `$_GET` — параметры query string;
- `$_REQUEST` — объединение `$_GET`, `$_POST` и `$_COOKIE` (использовать не рекомендуется из-за неоднозначности источника);
- `$_FILES` — загруженные файлы (нужны `enctype="multipart/form-data"`);
- `$_SERVER` — служебные данные, например `$_SERVER['REQUEST_METHOD']`, по которому определяется метод запроса;
- `$_COOKIE`, `$_SESSION` — cookie и сессия.

Чекбоксы с именем `tags[]` приходят в `$_POST['tags']` как массив; если ни один не отмечен, ключа в массиве нет, поэтому нужен `?? []`.

### 3. Как обеспечить безопасность при обработке данных из формы (например, защититься от XSS)?

Основной принцип: **никогда не доверять пользовательским данным**.

1. **XSS** — экранировать вывод через `htmlspecialchars($s, ENT_QUOTES, 'UTF-8')` в момент вывода в HTML. Экранировать нужно и значения, подставляемые обратно в форму. Дополнительно помогает заголовок `Content-Security-Policy`.
2. **Валидация на сервере** — проверка типов, длины, формата и обязательности; клиентская проверка только удобство.
3. **Белые списки** — для enum-полей, имён колонок сортировки, имён файлов.
4. **SQL-инъекции** (при работе с БД) — подготовленные запросы (PDO prepared statements), а не конкатенация строк.
5. **CSRF** — токен в форме, проверяемый на сервере, и `SameSite` для cookie.
6. **Загрузка файлов** — проверка MIME-типа и размера, переименование файла, хранение вне публичного каталога.
7. **Прочее** — `declare(strict_types=1)`, отключение вывода ошибок на продакшене, блокировка файла при записи, паттерн Post/Redirect/Get.
