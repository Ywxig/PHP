## Что сделано

Реализовано приложение на PHP 8+ с объектно-ориентированной архитектурой. Все классы лежат в одном файле `index.php` (разрешено условием). Приложение умеет:

- хранить транзакции (`TransactionRepository`);
- добавлять и удалять транзакции;
- искать транзакцию по `id`;
- сортировать по дате и по сумме (по убыванию);
- считать общую сумму, сумму за период, количество транзакций по получателю;
- выводить данные HTML-таблицей (`TransactionTableRenderer`).

Классы и интерфейс:

| Элемент | Тип | Ответственность |
|---|---|---|
| `Transaction` | класс | данные одной транзакции + расчёт дней с момента операции |
| `TransactionStorageInterface` | интерфейс | контракт хранилища (4 метода) |
| `TransactionRepository` | класс | хранение и базовый доступ, реализует интерфейс |
| `TransactionManager` | класс | бизнес-логика: суммы, подсчёты, сортировки |
| `TransactionTableRenderer` | `final` класс | только генерация HTML-таблицы |

Зависимости направлены так: `TransactionManager` → `TransactionStorageInterface` ← `TransactionRepository`. Менеджер не знает о конкретном репозитории.

## Задание 1. Строгая типизация

Первая строка кода в файле после `<?php`:

```php
declare(strict_types=1);
```

Теперь PHP не приводит типы молча: передача, например, строки `"5"` в параметр `int` вызовет `TypeError`. Директива действует на вызовы функций, сделанные из этого файла.

## Задание 2. Класс Transaction

Свойства (все `private`, задаются только через конструктор, используется promoted properties из PHP 8):

| Свойство | Тип | Смысл |
|---|---|---|
| `id` | `int` | уникальный идентификатор |
| `date` | `DateTimeImmutable` | дата транзакции |
| `amount` | `float` | сумма |
| `description` | `string` | описание платежа |
| `merchant` | `string` | получатель платежа |
| `merchantCategory` | `string` | категория получателя (см. [допущения](#принятые-решения-и-допущения)) |

Getter-методы: `getId()`, `getDate()`, `getAmount()`, `getDescription()`, `getMerchant()`, `getMerchantCategory()`. Сеттеров нет, поэтому объект после создания не меняется.

Метод `getDaysSinceTransaction(): int`:

```php
$today = new DateTimeImmutable('today');
$date = $this->date->setTime(0, 0);
return (int) $date->diff($today)->days;
```

- и «сегодня», и дата транзакции приводятся к полуночи, чтобы время суток не искажало результат;
- `diff()->days` — полное число дней между датами (всегда неотрицательное);
- для транзакции сегодняшним числом результат `0`.

## Задание 3. Класс TransactionRepository

- Массив `private array $transactions` — прямого доступа снаружи нет.
- Массив индексируется по `id`, поэтому `findById` и `removeTransactionById` работают за O(1).
- Методы:
  - `addTransaction(Transaction $transaction): void` — кладёт транзакцию по ключу `id`. Если такой `id` уже есть, запись заменяется (дубликатов не бывает).
  - `removeTransactionById(int $id): void` — `unset`; если `id` нет, ничего не происходит и ошибки нет.
  - `getAllTransactions(): array` — возвращает `array_values(...)`, то есть список с ключами 0..N-1. Это копия массива (массивы в PHP передаются по значению), так что внешний код не может испортить внутреннее состояние через неё.
  - `findById(int $id): ?Transaction` — возвращает объект или `null`.
- Репозиторий ничего не считает и не сортирует — только хранение и доступ.

## Задание 4. Класс TransactionManager

Конструктор:

```php
public function __construct(private TransactionStorageInterface $repository) {}
```

(после задания 7 — с интерфейсом). Менеджер сам транзакции не создаёт и не хранит, при каждом вызове берёт данные через `getAllTransactions()`.

| Метод | Что делает |
|---|---|
| `calculateTotalAmount(): float` | `array_sum` по суммам всех транзакций |
| `calculateTotalAmountByDateRange(string $startDate, string $endDate): float` | сумма за период; границы **включительно** (начало с 00:00:00, конец до 23:59:59) |
| `countTransactionsByMerchant(string $merchant): int` | количество транзакций получателя, регистр не важен (`mb_strtolower`) |
| `sortTransactionsByDate(): Transaction[]` | по дате, от старых к новым |
| `sortTransactionsByAmountDesc(): Transaction[]` | по сумме, по убыванию |

Особенности:

- сортировка выполняется над копией списка, порядок в репозитории не меняется;
- для сравнения используется оператор `<=>` (для дат и чисел);
- приватный вспомогательный метод `parseDate(string): DateTimeImmutable` превращает строку в дату и при ошибке бросает `InvalidArgumentException` с понятным сообщением;
- если начальная дата позже конечной, также бросается `InvalidArgumentException`.

## Задание 5. Класс TransactionTableRenderer

- Объявлен как `final class`, отвечает только за вывод.
- `render(array $transactions): string` возвращает готовую HTML-таблицу со столбцами:
  1. ID транзакции;
  2. Дата (формат `Y-m-d`);
  3. Сумма (формат `1 250.50`);
  4. Описание;
  5. Получатель;
  6. Категория получателя;
  7. Дней с момента транзакции.
- Все текстовые поля проходят через `htmlspecialchars(..., ENT_QUOTES, 'UTF-8')` в приватном методе `escape()` — защита от XSS и поломки разметки.
- В основной части файла только вызовы `render()` и вывод через `<?= ... ?>` (это короткая запись `echo`). Выводятся три таблицы: все транзакции, сортировка по дате, сортировка по сумме.

## Задание 7. Интерфейс TransactionStorageInterface

Интерфейс содержит четыре метода:

```php
interface TransactionStorageInterface
{
    public function addTransaction(Transaction $transaction): void;
    public function removeTransactionById(int $id): void;
    public function getAllTransactions(): array;
    public function findById(int $id): ?Transaction;
}
```

Что изменено:

1. `TransactionRepository implements TransactionStorageInterface`.
2. Конструктор `TransactionManager` принимает `TransactionStorageInterface`, а не конкретный класс.

Теперь можно написать другое хранилище (файл, БД, тестовая заглушка) и передать его менеджеру без единой правки в `TransactionManager`.

## Документация кода (PHPDoc)

У каждого класса, интерфейса, метода и свойства-массива есть PHPDoc-блок:

- описание назначения;
- `@param` с типом и смыслом каждого параметра;
- `@return` с типом и смыслом результата (для массивов — `Transaction[]`);
- `@throws` там, где метод может выбросить исключение;
- в репозитории применён `{@inheritdoc}`, чтобы не дублировать описание из интерфейса.

## Принятые решения и допущения

1. **Категория получателя.** В условии у `Transaction` перечислено пять свойств, но таблица должна содержать «категорию получателя». Чтобы она бралась из данных, а не выдумывалась в рендерере, добавлено шестое свойство `merchantCategory` с getter-ом. Если преподаватель требует строго пять свойств, категорию можно вынести в справочник `merchant => category` внутри рендерера.
2. **DateTimeImmutable вместо DateTime.** В подсказке указан `DateTime`; использован его неизменяемый вариант, чтобы дату нельзя было изменить снаружи через getter. API для задач лабораторной одинаков.
3. **Дубликаты id.** Репозиторий при добавлении с существующим `id` заменяет запись. Если нужно запретить, достаточно бросать исключение в `addTransaction`.
4. **Границы периода включительно**, регистр в имени получателя не учитывается.
5. **Деньги в `float`.** По условию методы возвращают `float`; в реальной банковской системе лучше хранить суммы в копейках (`int`) или использовать `bcmath`, чтобы избежать ошибок округления.
6. Всё в одном файле `index.php` — по разрешению условия.

## Ответы на контрольные вопросы

### 1. Зачем нужна строгая типизация в PHP и как она помогает при разработке?

По умолчанию PHP сам приводит типы: строка `"10"` спокойно превращается в число. Это может скрыть ошибки. С `declare(strict_types=1)` тип аргумента или возвращаемого значения должен совпадать с объявленным (исключение: `int` можно передать в `float`), иначе будет `TypeError`.

Польза:

- ошибки находятся сразу в месте возникновения, а не где-то далеко по цепочке вызовов;
- код предсказуемее и проще читается: по сигнатуре видно, что метод принимает и возвращает;
- IDE и статические анализаторы (PHPStan, Psalm) точнее подсказывают и проверяют код;
- меньше неявных преобразований, которые приводят к тонким багам.

В работе: нельзя передать в `removeTransactionById(int $id)` строку `"3"`, а `calculateTotalAmount()` гарантированно вернёт именно `float`.

### 2. Что такое класс в ООП и какие основные компоненты класса вы знаете?

Класс — шаблон (описание) для создания объектов: он задаёт, какие данные объект хранит и что умеет делать. Объект — конкретный экземпляр класса.

Основные компоненты:

- **свойства** (поля) — данные объекта (`private int $id`);
- **методы** — поведение (`getDaysSinceTransaction()`);
- **конструктор** — инициализация при создании (`__construct`);
- **модификаторы доступа** — `public`, `protected`, `private`;
- **константы класса** (`const`) и **статические** члены (`static`);
- также: деструктор, магические методы, трейты, абстрактные методы, наследование (`extends`), реализация интерфейсов (`implements`).

В работе: `Transaction` — класс с приватными свойствами, конструктором, getter-ами и методом расчёта.

### 3. Что такое полиморфизм и как он реализуется в PHP?

Полиморфизм — способность работать с разными объектами через единый интерфейс, когда конкретное поведение определяется типом объекта во время выполнения.

В PHP реализуется:

- через **интерфейсы** — разные классы реализуют один контракт;
- через **наследование и переопределение методов** (в том числе абстрактных классов);
- через утиную типизацию и union-типы (менее строго).

Перегрузки методов по типам аргументов, как в Java или C++, в PHP нет.

В работе: `TransactionManager` принимает `TransactionStorageInterface`. Ему можно передать `TransactionRepository`, файловое хранилище или тестовую заглушку — он вызывает одни и те же методы, а реальное поведение зависит от переданного объекта.

### 4. Что такое интерфейс в PHP и чем он отличается от абстрактного класса?

Интерфейс — контракт: набор сигнатур публичных методов (и констант) без реализации. Класс, который его реализует (`implements`), обязан определить все методы.

| | Интерфейс | Абстрактный класс |
|---|---|---|
| Реализация методов | нет | может быть (обычные и абстрактные методы) |
| Свойства | нет | есть |
| Множественность | класс реализует несколько интерфейсов | класс наследует только один |
| Ключевое слово | `implements` | `extends` |
| Конструктор | не задаётся | может быть |
| Модификаторы методов | только `public` | `public`, `protected` (и `private` у обычных) |
| Назначение | «что объект умеет» | «общая база» с частью готового кода |

### 5. Какие преимущества даёт использование интерфейсов? Пример из работы

Преимущества:

- **слабая связанность**: код зависит от контракта, а не от конкретного класса;
- **заменяемость**: реализацию можно поменять без правки клиентов;
- **тестируемость**: легко подставить заглушку (mock);
- **расширяемость**: новые реализации добавляются без изменения старого кода (принцип открытости/закрытости, инверсия зависимостей из SOLID);
- интерфейс чётко документирует, что требуется от хранилища.

Пример: `TransactionManager` зависит от `TransactionStorageInterface`. Сегодня данные лежат в массиве внутри `TransactionRepository`. Если завтра понадобится хранить их в файле JSON или в базе данных, достаточно написать новый класс, реализующий интерфейс (`JsonTransactionStorage`, `DbTransactionStorage`), и передать его в конструктор менеджера. Код `TransactionManager` и `TransactionTableRenderer` при этом не меняется.
